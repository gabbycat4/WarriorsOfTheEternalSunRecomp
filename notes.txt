## Dungeon "can't move forward" (Nov 22)
Cause: JMP (d8,PC,Xn) into a table of 4-byte code stubs (one instruction + BRA to a
common join, last stub falls through), indexed by facing*4. Example $010380:
  andi.w #3,d2 / asl.w #2,d2 / jmp 2(pc,d2.w) / subq.w #1,d1;bra / addq.w #1,d0;bra /
  addq.w #1,d1;bra / subq.w #1,d0 / join $010396
The recompiler only knew uniform Duff's devices and dc.w offset tables, so these were
INTERIOR_UNRESOLVED -> hybrid_jmp_interpret -> floor capsule declined -> step skipped.
10 sites: $010384 $010680 $011660 $011DC4 $011E2E $020022 $020130 $02066E $021526 $021D8A.
Fix: probe_stub_table_rom() in m68k-recomp-core profiles/genesis/code_generator.c
(seeding at scan time + in-function switch at codegen). Audit: INTERIOR_UNRESOLVED 7 -> 0,
in_function_switch 0 -> 10. Saved as patches/m68k-recomp-core-stub-jump-tables.patch
(applied in the submodule working copy; upstream candidate for mstan/m68k-recomp-core).
Evidence before this rebuild copied to evidence/2026-11-22/.

## Graveyard: "...the water was cursed." then stuck (Nov 22)
floor_unsafe $00D114 (session 3 frame 10374): run_at $00D114 exit $00CDDC expected $840034.
$00D106: MOVEM.L d1-d2/a0,-(sp) (12 B); ADD.W d0,d0; JMP 2(pc,d0.w) -> $00D110:
BRA.S $D148, BRA.S $D148, then index 4 lands on inline code at $00D114 (not a function).
The floor ran it correctly to the real return $00CDDC (after BSR $00D106 at $00CDD8),
but checked against the top of stack (saved D1) -> "unsafe", declined -> event code
skipped -> script stuck.
Fix (runner/glue.c): hybrid_jmp_interpret arms (target, A7); genesis_log_dispatch_miss
reads the expected return BELOW the routine's carried push (-g_split_sp_popped bytes,
available since the codegen stack-carry fix) and clears the carry on success.
patches/segagenesisrecomp-floor-jmp-tail-return.patch.
Possible later codegen improvement: BRA.S table + inline last case as an in-function switch.

## Grave text boxes never close (Nov 22) -- not the jump fix above
"He quenched his thirst..." / "Here lies Louise..." boxes: BlastEm closes them with one
press; recomp (native AND interpreter) never does, except rarely. Probe (tools/wotes_probe.py,
build/debug.ini enables the debug port 4400) showed the game running normally, per frame:
  |frame boundary| char path work | $5DE2 | PAD read (party panel $00EAC8) | WAIT $BA70 |
  V-int | PAD read (text box loop $004846: jsr $5DE2 / jsr $B91C / andi #$F0 / beq) | ...
$B93C keeps "new presses" = held & ~previous (masked by $FF8005 = $F0 for A/B/C/Start).
Engine applied new controller state at raster line 0 (machine_set_pad before
machine_run_frame_ex); the game overruns the frame, so the party-panel read after line 0
always took every new press and the text box only saw "already held".
Fix: GameSpec.pad_latch_at_vint (opt-in, default 0 = unchanged): machine_set_pad holds the
state until the vblank line and applies it right before the V-int (BlastEm-like).
wotes_spec.c sets it. Engine patch now: patches/segagenesisrecomp-wotes-fixes.patch
(floor JMP-tail return slot + pad latch).

## Phase 2: measure (started Nov 23)
game/wotes_motion.c: WOTES_MOTION_LOG=<file> writes one block per wall frame (format in the
file header): main-loop passes ("it", counted by a game_hook at the main-loop top $000608),
pad, all VDP regs, VSRAM A/B, hscroll A/B + per-line table hash, CRAM hash, sprite table in
link order, and every changed 68000 RAM byte (first frame: full RAM). Off when unset.
Logs go to measurements/ (git-ignored).

### Phase 2 result 1: world map (measurements/worldmap-1.log, Nov 23, 6036 frames)
- Game logic: main loop passes once EVERY frame on the map (it=1); battles run their own loop
  (it=0 there), as do title/menus. Not a 20 Hz map.
- Camera: exactly 1 px per frame while walking, every frame, H/V/diagonal; planes A and B
  together (no parallax). Stops only when blocked.
- Party leader (tile $4F8): fixed at screen centre; world step exactly 1 px/frame (119/119,
  229/229): perfectly even.
- Followers ($508/$510/$518): mostly 1 px/frame in the walk direction, but 10-30% of frames
  are 2 px or diagonal side-steps (they trace the leader's path round corners); very few
  reversals. NPC ($318): 0/1 px steps.
- Sprite list order changes between frames (Y sort): track by tile/owner, not slot.
=> At 60 Hz the map is already as smooth as the game's data allows. 240 Hz in-betweens
   (2x/4x render) would only reduce hold blur (1 px spread over 4 pictures) and soften the
   followers' 2-px side-steps. Modest gain; decide after dungeon + battle measurements.

### Phase 2 result 2: dungeon (measurements/dungeon-1.log, 4862 frames)
- Own loop (main-loop counter 0), scroll registers never change: no scrolling, no sliding turns.
- View redrawn into RAM (frames with >1000 RAM bytes changed): every step forward AND every
  turn = 2 redraws 8 frames apart (+1/+9 after the press); held button: a step every ~17
  frames (~3.5 steps/s). Likely a half-step view + the arrived view.
- Caveat: counted RAM redraws, not screen pictures. Motion log v2 adds "vh" (whole-VRAM hash)
  to confirm with a short new dungeon recording.
=> Arcana case: sliding can't make in-between views. Options: A keep the game's frames
   (240 = steadier pacing only), C our own 3D renderer (separate big project).

### Phase 2 result 3: battle (measurements/battle-1.log, battle ~frames 3150-9200)
- Battles on the overhead map, own loop. No palette flashes in this fight.
- Combatants: jump a whole 8 px tile every 9 frames (~6.7 steps/s), nothing in between
  (tiles $498, $510, $518). Attack lunge: 6 px out, back 12 frames later.
- Camera pans: 2-4 px per frame in short bursts. Projectiles/effects ($6B0): 6 px every frame.
=> Biggest smoothing payoff in the game: 8 px hops -> glides over 9 frames (36 pictures at 240),
   smoother pans and projectiles. Same method as Lagoon (interpolate between game steps,
   owners by tile/palette, one step of presentation delay).

### Phase 2 summary / decision
Priority for Phases 3-4: battle movement + battle camera, then map (hold blur, follower
side-steps). Dungeon: option A unless we later choose the 3D project. First Phase 3: second
core + in-between picture support in the Genesis engine (doesn't exist yet).

### Phase 2 result 2b: dungeon confirmed with VRAM hash (measurements/dungeon-2.log)
Each step = 2 new views ~8 frames apart, each uploaded over 1-2 frames (VRAM changes +0/+1 and
+8/+9); turns = 2 views, each uploaded over ~4 frames. No scroll, no gradual animation.

## Phase 3: presentation (started Nov 24)
The engine ALREADY has host-only interpolation for cartridge games (runner/main.c ~4320):
a display clock independent of the 59.94 Hz guest clock issues 2-4 pictures per tick at
fractional phases, VSync off, late pictures dropped (never queued), GENESIS_PRESENT_TRACE=file
logs every picture (frame, count, phase, interpolated, perf counter, image hash). It is on
only when g_game_spec.video->interpolate exists and settings "High refresh rate" (in-game menu
Esc -> Mods; settings.ini [video] presentation_rate = 120 | 144 | -1 display rate) is set.
Capture: GameVideo.presentation_capture gets every completed row with GVDPRasterRow layers
(plane A/B, sprites, priorities, host palette) -> the base for Phase 4 in-betweens.
So our Phase 3 = wire a WotES adapter (game/wotes_video.c, GameSpec.video) and measure pacing
at 240 before deciding whether the second core / pinning from nesrecomp dd2-240hz is needed.
Step 1: adapter with interpolate() returning 0 (pictures repeat) -> pacing test.
Phase 3 result (measurements/pacing-1.csv + .stderr.txt, Nov 24, 240 Hz "Display refresh rate",
pictures repeating): 19,300 pictures over 4,820 ticks = 4.004/tick (4 x 4800, 5 x 20);
interval median 4.167 ms, p99 4.218, max 4.429; 0 intervals > 6.25 ms (no skipped/late
pictures). => The engine's single-thread presentation is enough at 240 Hz; no second core /
pinning needed (native code is light). Watch drawing cost when Phase 4 draws real in-betweens.
Phase 4 step 4.1 (Nov 24): game/wotes_video.c keeps, per completed frame, a COPY of the VDP state
(captured at the last visible row) + the real picture + extra host colours. interpolate() renders
the copy with the engine's own gvdp_render_scanline, palette rebuilt like genesis_machine.c
colour_cb (0-63 normal, 64-127 shadow, 128-191 highlight via genesis_dac, host colours from
GVDP_HOST_PALETTE_BASE), compares with the real picture and shows ours only on an exact match.
No motion yet. WOTES_VIDEO_LOG=1 logs a self-check line once a second. Safe with HD: the runner
never calls interpolate() for the HD texture.
Phase 4.1 result (measurements/selfcheck-1.*): re-render == real picture in 36,025/36,033
pictures (the 8 differing were all in the first second, startup); pacing median 4.166 ms,
max 5.94 ms, 0 late. Re-render approach is pixel-exact and cheap enough.
Phase 4.2 (Nov 24): motion in game/wotes_video.c. Camera = plane scroll interpolated prev->latest
(hscroll table entries per mode 0/2/3, VSRAM full/column; >32 px = cut). Sprites = tracked
objects in WORLD coords (screen + camera: wx = sx - hs, wy = sy + vs), matched by tile group +
palette, then palette + size (animation frames), nearest within 48 px. Each object learns its
step period (median of last 4 gaps, 1..12): walkers ease over 1 frame, battle hops glide over
their 9 frames (up to one step of visual delay, input unaffected). Jumps > 16 px in one frame
(side-panel arrow 48 px between party boxes, teleports) = cuts. Self-check once a second
(unmoved render == real), WOTES_VIDEO_MOTION=0 = self-check only. Output is native resolution
(whole pixels): the map's 1 px/frame can't get finer (half pixels need a 2x path later).
Offline replay tools/glide_replay.py (same rules, 4 pictures/frame):
  battle-1 3150-9200: moves of 4+ px 983 per real frame -> 0 per picture (all steps 0/1/2 px)
  worldmap-1 960-3360: 21 -> 0

== Phase 4.3: quarter-pixel in-between pictures (2026-11-24) ==
Engine (segagenesisrecomp fork, not yet committed): GameVideo gains
presentation_scale() and interpolate_scaled(); main.c high_refresh loop draws
those into its own w*S x h*S nearest-scaled texture (colour LUT, trace hash
sampled 1 px per native block, png snap all handle the scaled size).
Adapter (game/wotes_video.c): camera offset and sprite positions rounded to
1/S px; planes captured once at the whole-pixel camera, sprites captured per
fraction group (max 4, link-order priority between groups), layers shifted
0/1 native px per sub-column/sub-row, composed with gvdp_compose_span; window
plane unshifted. x=0 mask sprites never moved (native path too).
Env: WOTES_VIDEO_SCALE=2..4 (default 4, 1 = off). Log line adds timing,
sprite groups, fallbacks and a phase-1 "4x-vs-real" exactness check.
Test: Step 26 -> measurements/quarter-1.*

Phase 4.3 result (measurements/quarter-1.*, Nov 24, Step 26): self-check 0 differ (158/158),
4x-vs-real mostly 0 (6/36 differed, small). Timing: avg 0.9 ms standing, 2-4 ms walking with
3-4 sprite groups, max 10.6 ms. Trace: 36,876 pictures / 11,493 ticks = 3.21 per tick (want 4);
1,495 intervals > 6.25 ms, 328 > 8.33 ms, clustered in walking stretches. User: 180-240 FPS,
small stutters, mountain shadows flicker "like Sonic 1's waterfall".
Cause 1: each picture re-ran the VDP renderer once per sprite group (up to 4) + composed up to
16 variants per row. Cause 2: mountain shading is a 1-px checker in plane tiles (worldmap-1.log:
reg12 always $81 = no shadow/highlight; sprite counts don't alternate), which flips with every
pixel of scroll; on a TV it blurred into one shade.
Phase 4.4 (game/wotes_video.c only): per-frame layer cache (8 sprite slots keyed by frame +
member entries/positions, 2 plane slots keyed by frame + whole-pixel camera I,J), groups with no
sprite on a row don't split that row into variants, dither blending: plane rows with ABAB runs
(4+ px) that continue on a neighbouring row are marked at capture; after compose, marked
non-sprite pixels in an RGB ABAB run get the A/B average. Exactness check now compares the
pre-blend picture. Log adds "captures N, reused M, dither px". WOTES_DITHER_BLEND=0 = off.
Test: Step 27 -> measurements/cache-1.*
